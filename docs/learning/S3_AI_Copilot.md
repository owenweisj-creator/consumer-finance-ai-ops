# S3 AI Copilot：带教笔记

## 一、为什么不能“直接把数据库接给大模型”

直接让 LLM 生成 SQL 并执行，会遇到四类问题：

1. **幻觉字段**：模型编造不存在的表或列。
2. **口径错误**：通过率用了错误的分母，或者对已算好的比率求平均。
3. **越权与破坏**：生成 DELETE、DROP 或访问敏感表。
4. **数字不可追溯**：报告里的数字和 SQL 结果对不上。

所以本项目采用“语义层 + 只读执行 + 校验 + 评测”的工程化链路。

## 二、NL2SQL 链路

```text
问题改写 → 语义层检索 → SQL 生成 → sqlglot 校验 → DuckDB 只读执行
→ 结果校验 → 自然语言解释 → 图表建议
```

每一层的职责：

- **语义层**：告诉模型有哪些视图、指标、维度、口径。
- **SQL 生成**：模型只负责“翻译”，不负责“定义”。
- **sqlglot 校验**：只允许 SELECT，只允许 `mart.v_*`，禁止多语句和注释。
- **只读执行**：DuckDB `read_only=True`，结果最多 200 行。
- **结果校验**：空结果、列数异常、分母为 0 都要提示。

## 三、RAG 知识库

知识库覆盖：

- 指标口径：通过率、用信率、不良率、Vintage。
- 业务规则：审批状态、时间映射、金额口径。
- AI 使用手册：适合/不适合的场景、提问模板、验证清单。

回答必须带引用，例如 `[metric_dictionary.md#审批通过率]`。没有依据时明确拒答，不编造。

## 四、Prompt v1 到 v2 的迭代

v1 的问题：

- 只说“生成 SQL”，没有强制拆解“指标 + 时间 + 维度 + 过滤”。
- 没有明确“比率不能求平均”。
- 没有拒答规则。

v2 的改进：

- 先拆解问题，再写 SQL。
- 明确分子/分母和重算规则。
- 增加少样本和“无法回答时返回 null”的规则。
- 增加视图白名单。

评测时要用同一套题对比 v1/v2，不能只看“感觉更好了”。

## 五、评测指标

- **执行成功率**：SQL 是否能跑通。
- **结果准确率**：结果与人工标准 SQL 是否一致。
- **拒答正确率**：不该回答的问题是否拒答。
- **危险 SQL 拦截率**：写操作、raw 表、多语句是否 100% 拦截。
- **延迟与成本**：p95 延迟、token 消耗。

## 六、你的动手任务

1. 写 5 道评测题，覆盖指标查询、趋势、对比、归因、拒答。
2. 评审 1 条模型生成的 SQL，指出它的分母是否正确。
3. 改一版 Prompt，至少增加一条约束，并用 5 道题对比结果。

## 七、面试追问

1. 你怎么防止模型生成 DELETE？
2. 模型生成的 SQL 能跑通，但结果不对，你怎么发现？
3. RAG 检索不到依据时，你会让模型猜吗？为什么？
