# PRD：消费金融经营分析 AI 助手

## 1. 背景

经营分析团队每月需要从申请、审批、用信、还款、逾期等多张表取数，手工拼接报表，再写解读和建议。当前痛点：

1. 取数依赖数据团队，业务问题从提出到拿到结果平均需要 1–3 天。
2. 指标口径分散在 Excel、SQL 和口头约定中，同一指标出现多个版本。
3. 报告中的数字和结论靠人工核对，异常归因依赖个人经验。
4. AI 问数如果直接连数据库，存在编造字段、越权查询和数字不可追溯的风险。

## 2. 产品目标

做一个面向经营分析、风险管理和业务负责人的内部 AI 助手，让业务人员用自然语言完成：

- 指标查询：本月通过率、用信率、件均、不良率。
- 趋势与对比：最近 6 个月走势、渠道/产品/地区对比。
- 异常归因：通过率变化中结构和比率各贡献多少。
- 报告初稿：周报、月报、专项分析的初稿与图表。
- 口径问答：指标定义、分母、使用边界。

**成功指标**：

- 40+ 题评测集 SQL 执行准确率 ≥ 80%。
- 危险 SQL 拦截率 100%。
- 报告数字一致性 100%。
- 单次月报生成时间 < 1 分钟（本机实测）。
- 试点用户 2 周内至少完成 3 次真实问数，采纳率 ≥ 60%。

## 3. 用户与场景

| 用户 | 核心场景 | 关键诉求 |
|---|---|---|
| 经营分析师 | 周报/月报、专项分析 | 快、口径统一、能直接用于会议 |
| 风险策略 | 通过率与不良率联动分析 | 能拆结构、能看 vintage |
| 业务负责人 | 渠道/产品经营诊断 | 不问 SQL，只要结论和行动建议 |
| 数据团队 | 语义层与指标治理 | 可审计、可扩展、少救火 |

## 5. 功能设计

### 5.1 问数

输入：自然语言问题。  
输出：SQL、结果表、自然语言解释、口径引用、耗时与 token。

链路：

```text
问题改写 → 语义层检索 → SQL 生成 → sqlglot 校验 → DuckDB 只读执行
→ 结果校验 → 自然语言解释 → 图表建议
```

### 5.2 报告

- 月报：核心指标、渠道/产品、风险与 vintage、异常与归因、行动建议。
- 周报：本周 vs 上周、渠道表现、下周行动项。
- 专项：审批通过率变化的结构/比率分解。

数字由 Python 计算并注入，LLM 只负责解释和建议；生成后做数字一致性校验，不一致自动回退模板。

### 5.3 知识库

覆盖指标口径、业务规则、AI 使用手册。BM25 检索，回答必须带 `[文件名#章节]` 引用；无依据时明确拒答。

### 5.4 异常与归因

- 异常：滚动中位数 + MAD 稳健 z 分数，阈值 2.5。
- 归因：渠道占比变化（结构效应）+ 渠道自身通过率变化（比率效应）。

## 6. 非功能需求

- 安全：不访问 `raw`，只允许 `SELECT`，结果最多 200 行，敏感字段屏蔽。
- 性能：单次问数 p95 < 15 秒；月报生成 < 1 分钟。
- 可追溯：每条 SQL、每个数字、每个引用都可回查。
- 可维护：Prompt 版本化，评测集固定，模型/Prompt 变更需记录指标变化。
- 可用性：看板离线可打开；Excel 无宏、可直接打开。

## 7. 上线与推广

1. **灰度**：先由本人和 2 位同事试用，每周收集 5 条问题。
2. **培训**：60 分钟培训，包含 3 个真实场景、1 个错误案例、1 个安全边界。
3. **知识库**：把指标口径、常见问题、SQL 模板沉淀到 `knowledge/`。
4. **采纳度量**：激活率、周活、人均问数、报告节省时间、口径争议次数。
5. **迭代**：每两周复盘一次失败问题，进入 backlog；Prompt 变更必须跑评测。

## 8. 风险与假设

- 数据为公开历史数据，业务日历为模拟映射，不能代表真实公司经营。
- `TARGET` 是 30+ 天逾期标签，不是核销率。
- 没有获客成本、资金成本和真实利润，不能计算 CAC、ROI、净利润。
- AI 可能生成看似合理但口径错误的 SQL，必须保留人工复核。
