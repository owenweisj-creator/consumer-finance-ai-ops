# 5 分钟项目讲解稿

## 0:00–0:30 背景

我做的项目叫“消费金融经营分析 AI Copilot”，是一个个人项目。起因是我在消费金融公司做数据分析时，发现三件事很耗时间：申请、审批、用信、还款、逾期分散在不同表；通过率变化说不清是渠道结构还是审批能力；业务想自己取数，但 AI 问数又容易编字段、错口径。

所以我用 Home Credit 公开数据，从 0 到 1 做了一套完整链路：数据仓库、经营分析、风险分层、AI 问数、看板、报告和产品化文档。

## 0:30–1:30 数据与指标

数据覆盖申请、历史申请审批、分期还款、POS/信用卡账本和征信。我用 DuckDB 建了星型模型，定义了 13 个核心指标，包括进件量、审批通过率、用信率、件均、平均期限、不良率、DPD30、复贷率。

这里有两个关键口径。第一，审批通过率的分母是全部进件，分子是 Approved 加 Unused offer；Unused offer 是“批了没用”，属于用信环节流失，不是拒绝。第二，用信率的分母是审批通过量，分子是实际用信量。这样拆开，才能分别看“批不批”和“用不用”。

## 1:30–3:00 关键发现

第一个发现：2026 年 9 月进件量 36,012 笔，环比增长 26.2%，但审批通过率从 29.4% 降到 22.9%，稳健 z 值是 -7.11，属于异常。

我没有直接说“风控变严”，而是做了渠道结构分解。Credit and cash offices 的申请占比从 60.3% 升到 65.1%，这个渠道通过率只有 7.84%，贡献了大约 -1 个百分点的结构效应；Country-wide 通过率 87.6%，但占比从 16.7% 降到 12.2%，贡献了大约 -2.75 个百分点。合计结构效应 -6.52 个百分点，说明主要是“低通过率渠道扩张、高通过率渠道收缩”，不是全渠道审批能力同步恶化。

第二个发现：审批金额增长 32.1%，但审批件数下降 1.8%，实际用信只增长 1.2%；件均增长 30.5%，平均期限增加 2.31 个月。增长是“价”驱动，不是“量”驱动。如果件均回落，金额增长不可持续。

第三个发现：Vintage 看，MOB 6 的累计 DPD30 大约 0.44%–0.49%，早期账龄风险可控。但 installments 的 DPD30 和 application_train 的 TARGET 不良率 8.07% 不是一个口径，前者是分期逾期，后者是 30+ 天违约标签，所以我在报告里明确不混用。

## 3:00–4:30 AI Copilot

AI 部分不是“把数据库接给大模型”。我的链路是：语义层 → NL2SQL → sqlglot 校验 → DuckDB 只读执行 → 结果校验 → 解释。

语义层用 YAML 定义指标、维度、口径和可用视图，模型只能查 `mart.v_*`，不能碰 `raw`。SQL 校验只允许 SELECT，禁止 DDL/DML、多语句、注释；执行时 read_only，结果最多 200 行。

我还做了 RAG 知识库，回答指标口径必须带引用；没有依据就拒答。报告里的数字全部由 Python 计算后注入，LLM 只负责解释，生成后做数字一致性校验，不一致就回退模板。

评测集 42 题，Prompt v2 的 SQL 结果准确率 85.3%，知识问答 87.5%，危险 SQL 拦截率 100%，平均延迟 1.3 秒。v1 是 82.35%，v2 提升了 2.94 个百分点，但 token 多了约 22.7%，所以我不会说“Prompt 越长越好”。

## 4:30–5:00 结果与反思

最后产出包括 HTML 看板、Excel 工作簿、周报/月报/专项报告、PRD、30 条 UAT、培训手册和 3 个 AI 创新提案。单次月报生成不到 1 分钟。

这个项目最大的收获不是“会调 API”，而是理解了 AI 落地的难点在口径、验证和采纳。我的定位是：AI 是队友，不是搜索引擎；我负责定义问题、给约束、验收结果，AI 负责加速实现。
